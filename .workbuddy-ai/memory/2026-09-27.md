# 2026-09-27 — Performance diagnosis + tenant isolation fixes

## Perf investigation (Next.js app feels slow)

Root causes found (database is Supabase `ap-northeast-1` = Tokyo; dev machine is
GMT+3, so ~200-300ms round-trip floor per query — this is the dominant cost):

1. **Cross-tenant data leak (security, not just perf).** `listMembers` and
   `listFunds` never applied a `tenantId` predicate (§6 violation). Every tenant
   saw every tenant's members/funds. Also prevented use of `idx_members_tenant`.
2. **Guaranteed-failing dropdown requests.** Client `useMemberOptions` sent
   `limit: 500` / `useFundOptions` `limit: 200`, but the Zod schemas capped
   `limit` at `max(100)`. Every dropdown request 400'd, then React Query retried
   (`retry: 1`) — doubling latency for a request that could never succeed.
   Compounded by `getPaginationParams` hard-clamping to 100 independently.
3. **Redundant second `/api/deposits` call.** Deposits header fetched up to 1000
   full deposit rows (with member/fund joins) purely to SUM them in the browser.
4. **Duplicated `/api/settings` fetchers** in 4 files (deposits/shared,
   members-list-view, member-detail-sheet, audit-logs-view). Same key so RQ
   deduped the network call, but shape was re-declared and drifted per file.
5. **All 21 `page.tsx` are `"use client"`**, 18 API routes `force-dynamic` — no
   server rendering/caching, so every screen pays JS-download-then-fetch.

## Superadmin panel versus (PathshalaPro vs InvestWise) — research deliverable

Compared both platform consoles at code level:

- **PathshalaPro `/system-admin`** (12 pages): layout gate via Node `getAuthContext`
  (SYSTEM_ADMIN role / platform-owner email / impersonated) + client re-check in
  `SystemAdminShell`; API side uses `requireApiAccess({allowSystemAdmin:true})` mega-guard
  that also blocks system admins from tenant APIs (strict plane separation), enforces
  subscription state and per-tenant module licensing (featureFlags + override, 60s cache).
  Extra surfaces InvestWise lacks: feature-flags, users, settings, templates pages;
  feature-flags/health/onboarding-templates/subscriptions(plans,end-date,run-expiry)/users APIs.
- **InvestWise `/admin`** (9 pages): 3-layer guard — edge middleware `/admin*` fence
  (`isPlatformEdge(claims)`, jose, no DB), server layout `verifyEdgeAccessToken` +
  `isSuperAdminRole`/`isPlatformOwnerEmail`, per-API `requireAuthUser`+`requireSuperAdmin`
  (lib/admin-guard.ts). No feature flags/licensing — full suite for every tenant.
- **Impersonation is the sharpest divergence**: PathshalaPro = cookie-swap into tenant
  (2h JWT replaces auth_token, tenant-targeted, captures IP/UA); InvestWise = dual-session
  model (30-min target-user token returned in response body, admin cookie session intact,
  revoke = token blacklist, START/END rows in super_admin_action_log, dedicated
  /admin/impersonate page). InvestWise model is the safer posture for real-money support.
- Verdict: page-count deltas are mostly legitimate use-case differences (school SaaS sells
  modules → needs flags/templates/plans; investment platform → needs sandboxed impersonation).
  Worth borrowing if needed: IP/UA capture on impersonation log; subscription expiry sweep
  (run-expiry) if tiering ever lands.
- AdminShell already carries "Pathshala-Pro System Admin styling" (other agent's port) —
  chrome converged, architecture intentionally not.
